## 受注・専用オーダーページ（B-171 / B-172）

### M-002 専用オーダーページの実務要件（慎太郎さん回答 2026-09-08）
- 記入: 2026-09-08
- 状態: 起票済み(BACKLOG B-171 / B-172 の定義欄へ昇格・2026-09-08)
- 経緯: B-172（クライアント認証・権限）の設計に入る前の実務ヒアリング3問への回答。
  read-only recon（RECON-D / RECON-E・2026-09-08）で判明した既存の器と突き合わせるために取った。

#### 原文（慎太郎さん 2026-09-08）
> 1、専用オーダーページに入るのは誰ですか。 クライアント企業で1アカウントを共有。
> 2、1ページに何品番を並べますか。SKUにもよるので、フレキシブルにできるといいですね。
> 品番カルテにも言えることですが、SKUでマトリックスの表が一番馴染みやすいです。
> 3、卸値、納期（表示と現実は異なる。）、進捗などはゆくゆく見せれれるといいと思うが、現状は不要。

#### 確定した実務要件
1. アカウントの単位は **クライアント企業に1つ（担当者で共有）**。担当者ごと・バイヤーごとではない。
2. 1ページに載せる品番数は **固定しない（フレキシブル）**。SKU 数によって変わる。
3. 先方に見せる UI は **SKU のマトリクス表** が最も馴染む。★品番カルテにも同じことが言える。
4. 先方に見せる情報は、現状は **品番・色・サイズ・数量まで**。
   卸値・納期・進捗は **ゆくゆく見せたいが現状は不要**（＝初版のスコープ外・将来の拡張）。
5. ★納期については「**表示と現実は異なる**」との但し書きがある。
   先方向けの表示納期と社内の実納期が別物であることを含意する。

#### ★recon で判明した既存実装との食い違い（2026-09-08 実測・要判断）
- `OrderPage.productId` は **必須**（nullable ではない）＝ schema 上は 1ページ＝1品番。
  上の 2（フレキシブル）と食い違う。実オーダーシートは1通20品番
  （sales-order-spec-addendum-v0_1 §0 の実測）。
  原設計は展示会・品番単位のページを想定しており、受注 spec v1.0 §0 の訂正
  （OEM に展示会積み上げの概念は無い）と同型の食い違いと思われる。
- `OrderPage.restrictedBuyers`（Json・buyer ID リスト）と `Buyer.clientId` が存在し、
  `OrderPageAccessType` に LINK_ONLY / PASSWORD_PROTECTED がある。
  原設計は「社外は User を作らず、URL＋パスワード＋Buyer 制限で入れる」方式だった可能性がある。
  ★上の 1（クライアント企業で1アカウント共有）は、この方式とも、
  User を作る方式とも両立しうる。どちらを採るかは B-172 の仕様確認書で決める。
- `User` に client / supplier / factory / buyer への参照列は **存在しない**（全文確認済み）。
- ★`middleware.ts` は存在せず、`src/app/(app)/layout.tsx` も auth() を呼んでいない
  （現物5行・AppShell を被せるだけ）。ルート単位の認証強制が無く、保護は各ページの実装依存。
  **(app) 配下に auth を強制していないページが無いかは未測定**（RECON-F 未実行）。

#### 未確定（B-172 仕様確認書 v0.1 で決めること）
- 1アカウント共有を、通常ログイン（User + 新規の client 紐付け）で実現するか、
  OrderPage の accessType（PASSWORD_PROTECTED 等）で実現するか
- SKU マトリクス表を B-171 の画面仕様としてどこまで定義するか
- 卸値・納期・進捗を「将来出す」ための器を初版から持つか、後から非破壊で足すか
