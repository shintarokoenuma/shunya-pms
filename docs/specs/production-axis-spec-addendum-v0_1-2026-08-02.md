## 0. 本追補を書いた理由

PR #115（2026-08-01）で品番カルテのセクション名を「サンプル製作」→「製作ラウンド」に
改名した際、コード上のコメントに **「量産ラウンドも含む実態に合わせ改名」** と記された。
しかしこれは production-axis v1.0 §2-1 の確定（量産製作セットは新設しない）と整合せず、
2026-08-02 の議論で **撤回**した。

撤回した判断が spec に残らないと、次に品番カルテを触る際に同じ議論を再生産する
（＝「色マスターの轍」）。よって本追補に確定事項として記録する。

## 1. 確定事項

### 1-1. 量産に「ラウンド」概念は無い（✓ 確定）

- サンプルは 1st → 2nd → 3rd と**同一品番内で複数回**繰り返す。だからラウンドが要る。
- 量産は**同一品番につき1回**。だからラウンドは要らない。
- 「量産製作ラウンド」「量産2ndラウンド」等の概念・モデル・UI は**作らない**。
  production-axis v1.0 §2-1「量産製作セット（SampleProduction の量産版モデル）は
  新設しない」の UI 側への帰結である。

### 1-2. 品番カルテの構造（✓ 確定）

```
品番カルテ（Product = 1つの社内品番）
├── サンプル製作ラウンド（SampleProduction）… 1st / 2nd / 3rd と複数
└── 量産 … 1回きり
```

**「品番カルテ ＝ 量産1回分」ではない。** カルテはサンプル群と量産の両方を抱える器。
サンプルは複数・量産は1回、というこの非対称が、片方にだけラウンドが要る理由である。

### 1-3. 追加生産は別 Product として派生する（✓ 確定）

初回生産の後に追加生産が発生した場合、**同一 Product に積まず、新しい社内品番
（Product）を派生させる**。親子は既存モデル `ProductRepetitionLineage` で結ぶ。

| | 初回生産 | 追加生産 |
|---|---|---|
| 社内品番 productCode | MK-26SS-TS-001 | MK-26SS-TS-002（**新規**） |
| 先方品番 clientProductCode | MARKA-25001 | MARKA-25001（**同じまま**） |

- `@@unique` は `[companyId, productCode]` のみで `clientProductCode` に一意制約は
  無い（live 確認 2026-08-01）。よって複数 Product が同じ先方品番を持てる。
- product-sample v1.0 §4-1(a)(b)(c)「社内品番が背骨／先方品番は別フィールド／
  表示で主従を切替」がこのケースをそのまま吸収する。先方から見れば品番は変わらない。

**別 Product にする理由（同一 Product に積まない理由）:**
1. `Product` は productionQty / plannedDeliveryDate / deliveredQty を**単数で**持つ。
   2回分を1つに入れると数量も納期も表現できない。
2. 追加生産は生地の再手配・別ロット・別納期・別請求になる。原価も回ごとに違う
   （値上がり・小ロット割増）。分けないと採算が見えない。
3. 色・サイズ追加の場合、SKU 構成そのものが変わる（Sku は productId 配下）。
   同一 Product に押し込むと初回分と追加分の SKU が混ざり、(C) 実績突合が崩れる。
4. 1 Product = 1 量産 が保たれることで、§1-1 のラウンド不要が成立する。

**単純な追加（色もサイズも同じ・数量のみ追加）も別 Product とする。** 判断基準は
「先方の発注書が別か」ではなく「**原価と納期を別に管理する必要があるか**」であり、
追加生産は必ず別になる（慎太郎さん確定 2026-08-02）。

### 1-4. リピート種別（既存 enum・変更なし）

```prisma
enum RepetitionType {
  EXACT_REPEAT        // 完全リピート（仕様変更なし）＝単純な数量追加
  MINOR_CHANGE        // 軽微な変更（色追加、サイズ追加等）
  MAJOR_CHANGE        // 大幅な変更（仕様変更、パターン修正必要）
  SEASONAL_VARIATION  // シーズンバリエーション
  COLLABORATION       // コラボバージョン
}
```

`ProductRepetitionLineage.changesData Json?` に `{colors_changed, sizes_changed,
spec_modified}` を持つ設計が既にある。色・サイズ追加はここで表現する。

### 1-5. UI 表現（✓ 確定・PR #118 で実装済み）

- 品番カルテのセクション見出し: 「製作ラウンド」→ **「サンプル製作ラウンド」**
- ボタン: 「サンプル作成」→ **「+ ラウンド追加」**
- 遷移先 `/samples/new` のページタイトル（「サンプル新規作成」）は**変更しない**。
  データモデルが SampleProduction であり `/samples` 配下は「サンプル」で一貫している。
  品番カルテ文脈でのみ「ラウンド」と言い換える。

## 2. 要件として記録（設計は未確定・B-102 で詰める）

### 2-1. リピート起票時のコピー要件（慎太郎さん要望 2026-08-02）

追加生産の品番を起こす際、親 Product から以下を引き継げるようにしたい。

| 対象 | 扱い | 備考 |
|---|---|---|
| 仕様（縫製指示 sewingInstructions 等） | **コピー** | B-094 で Json 1本になったのでコピーは容易 |
| BOM の生地行 | **コピー** | 素材・用尺・ロス率等 |
| BOM の付属行 | **コピー** | |
| カラーウェイ / SKU 構成 | **要検討** | MINOR_CHANGE では変わる。EXACT_REPEAT ではコピー |
| 納期（desired/planned/actual） | **ブランク** | 慎太郎さん確定。引き継がない |
| 数量（productionQty 等） | **ブランク** | 回ごとに異なる |
| 発注伝票（PO/WO）・SampleProduction | **コピーしない** | 伝票は回ごとに新規 |
| 過去のコスト | **参照表示（コピーではない）** | §2-2 参照 |

### 2-2. コストは「コピー」ではなく「参照表示」（設計上の重要な区別）

慎太郎さんの要望は「**過去の金額がわかると確認しやすい**」。これは金額を新品番に
焼き込むことではなく、**前回いくらだったかを横に並べて見せる**こと。

- 金額をコピーして固定すると、生地の値上がり・小ロット割増・為替変動を見落とす。
- production-axis v1.0 §1-4 の PE seed① は「単価＝ seed のコピー値、人が微調整」と
  いう形を採っており、**コピー値＋出所明示＋人が確認**という前例がある。
  リピートでも同じ思想を採り、「前回値」を必ず可視化した上で人が確定する。
- 実装の形（前回値カラムを並べるか・差分バッジを出すか）は B-102 で決める。

### 2-3. 未確定の論点（B-102 の仕様確認で詰める）

- `ProductRepetitionLineage` は**休眠モデル**（src 参照の有無は着手時に live 確認）。
  実装範囲（起票 UI・系譜表示・ModelCode 累積の自動更新）をどこまでやるか。
- リピート起票の導線をどこに置くか（品番カルテの操作メニュー / 一覧 / ModelCode 詳細）。
- コピーの粒度（全部コピーして消させるか、選択式か）。
- 社内品番の採番。同一 ModelCode・同一シーズンで連番が進むのか、別シーズンになるのか。
- `ModelCode.totalRepetitions` / `latestProductId` の更新タイミング（phase1a-12 §9.2 で
  Phase 1B 送りとされたまま未実装）。

## 3. 量産の進行管理（方向性のみ・B-101 で詰める）

`ProgressTask` は設計段階から `phase: SAMPLE / PRODUCTION` を持ち、PRODUCTION 側の
taskType（GRADING / SHIPPING / DELIVERY / INVOICE）が**箱だけ存在し未実装**。
量産に入った後の進行を追う場所が現状どこにも無い。

**方向性（未確定）**: 新しいボックスを増やさず、品番カルテの「ステータス履歴」
セクションを「進行」セクションに拡張する案（慎太郎さん提案 2026-08-02）。

```
【進行】セクション
├─ 進行チェックリスト（現在の状態・編集可）
│    Product.status がサンプル期 → phase=SAMPLE のタスク
│    Product.status が量産期     → phase=PRODUCTION のタスク
└─ ステータス履歴（過去の記録・追記のみ・read-only）
```

- `ProductStatusHistory` は追記専用のイベントログ、`ProgressTask` は書き換える
  状態テーブル。性質が逆なので**同じ行に混ぜない**。同一カード内で上下に分ける。
- B-096（進行表ボード＝品番×工程マトリクス）と同じ `ProgressTask` を参照するため
  二重管理にならない。**B-101 と B-096 は同時設計する。**
