## 0. 結論

1. **目標は shunya-pms を請求の正にすること。当面は KKAP+ と併用**し、KKAP+ には人が入力して突き合わせる（D-18）。shunya-pms から KKAP+ の DB へは書き込まない。
2. **納品書**: サンプル（既存）に加えて**量産**を扱う。量産は受注から SKU で引き当て、**1 SKU＝1行**（D-19）。売値は**納品の時に行ごとに直す**（D-2・D-19）。
3. **合計請求書**: クライアント × 締めの期間で、**納品完了（DELIVERED）以降**の納品書の明細を、**サンプル・量産の区別なく合算**して1枚にする（D-4・D-6）。
4. **納品前の請求**: デポジット＋COD は設定％、前払い・代引きは 100% を**納品前に請求**。金額は人が入れる（D-7・D-8）。納品後の請求書で**前受金を差し引く**（D-20）。L/C・カスタムは扱わない（D-9）。
5. **入金**を記録する（D-11）。**納品書 PDF と請求書 PDF**をそろえて作る（D-12）。
6. **締め**: 取引先ごと・月ごとにロック（D-13・D-16）。発注は発注日で切る（D-14）。締めた期間は新規・編集・削除すべて不可（D-21）。締めは誰でも、解除は管理者だけ（D-15）。

## 2. 設計

### 2-1. 量産の納品書（B-114）

- 引き当てダイアログ（今は SAMPLE / ORDER＝発注明細の2タブ）に **「受注（量産）」タブ**を足す。
  - 選んだクライアントの受注（CONFIRMED 以降）→ SKU ごとに「受注数・納品済み・残り」を出す → 今回の数量を入れて追加。
  - 追加された明細: `skuId`（★量産は必須・アプリ側で担保＝B-108 §3-1 の申し送り）/ `productId` / `soId` / `soItemId`（休眠列を起こす）/ colorName / size / quantity / `unitPrice`。
- **単価の初期値は受注明細の単価（SoItem.unitPrice）**。人が行ごとに直す（D-2・D-19）。受注の単価と違う行は画面で色を変える（参考画面の「売値を直した行」）。
- 受注・量産見積の単価は書き換えない（受注時の約束と納品時の確定を両方残す）。
- **D-17 の反映**: 納品書を DELIVERED にした時、`SoItem.deliveredQuantity` / `remainingQuantity` と `Sku.deliveredQuantity` を更新する。
  - ★技術判断: 加減算ではなく「その SoItem に紐づく DELIVERED 以降の納品書明細の合計」から**毎回算出し直す**（受注の `recomputeSkuOrderedQuantities` と同じ考え方）。DELIVERED から戻す・取消した時も同じ関数で正しい値に戻る。
- 対象は `updateDeliveryNoteStatus`（今は UI 4値・遷移制約なし・AuditLog あり）。

### 2-2. 合計請求書（B-109・月次）

1. 請求書の新規作成で **クライアントと期間**を選ぶ。期間は `Client.closingDay` から自動で出し、人が直せる（例: 31 → 前月末の翌日〜当月末／20 → 前月21日〜当月20日）。
2. 候補 = そのクライアントの **DELIVERED 以降の納品書**のうち、納品日（`deliveryDate`）が期間内で、**まだ取消されていない請求書に載っていない明細**。サンプル・量産を区別しない。
3. 人が確認して（外す行は外せる）保存 → `INV-{年}-{4桁}` を採番（DLV と同型・論理削除も母数）。種類は `STANDARD`。
4. 明細は納品書明細の**スナップショット**（納品日・先方品番・品名・色・サイズ・数量・単価）＋ `deliveryNoteItemId`。見せ方は案A（D-19）。
5. 支払期日 = 締め日と `paymentMonthOffset` / `paymentDay` から自動計算・人が直せる。
6. 請求先 = `Client.billing*` → `Client` 基本（B-108 §4-2 の連鎖）をスナップショット。
7. 発行者 = `COMPANY_PROFILE` 定数に **登録番号 T2011001051698** を足し、`issuerName` / `issuerAddress` / `issuerTaxId` にスナップショット。
8. **二重請求の防止**: 1つの納品書明細は、取消されていない請求書に1回だけ。候補から除外し、保存時にサーバでも確かめる。

### 2-3. 納品前の請求（D-7・D-8）と前受金の差し引き（D-20）

- 取引条件が DEPOSIT_COD / ADVANCE_PAYMENT / CASH_ON_DELIVERY のクライアントは、**受注から「先の請求書」**を作れる（種類 `DEPOSIT`・`primarySoId` に受注）。
  - 金額は人が入れる。横に参考値（受注の合計、デポジットは × `Client.depositPercentage`）を出す。
- 納品後の請求書（2-2 と同じ作り方）では、同じ受注の先の請求書を候補に出し、選ぶと**最後に「前受金（INV-○○）」を差し引く行**が入る。差額が 0 ならご請求額 0 円。
- ★**確認事項 K-1（税理士事務所）**: 前受金に消費税をどう載せるか（先の請求書で税を載せるか・差し引く行の税区分）。実装は「差し引く行の税の扱い」を1か所にまとめ、確認できたら値を決める。
- LETTER_OF_CREDIT / CUSTOM のクライアントは、請求書の作成画面で「この取引条件は v1 では扱っていません」と出す（D-9）。

### 2-4. 消費税（インボイス制度）

- 明細ごとに税率・税区分（既定 10% = `STANDARD_10`）。**消費税額は請求書1枚につき税率ごとに1回だけ端数処理**して、`taxableAmount10` / `taxAmount10` ほかに入れる。
- **端数処理の向きは Q-3（KKAP+ の設定）**。定数1か所に置き、決まったら値だけ入れる。★それまでの仮の値は、実装ブリーフで「未確定」と明記した上で置く。
- ★既存の納品書は明細の小計を Math.round で出している（delivery-notes.ts:462）。請求書の税計算とは別物（税は請求書側で1回）。

### 2-5. 請求書の状態・訂正

- 使う状態: DRAFT（作成中・編集可）→ SENT（送付済み＝確定）→ PARTIALLY_PAID / PAID ／ CANCELLED。承認・ACKNOWLEDGED・OVERDUE・REFUNDED・WRITTEN_OFF は v1 では出さない（enum は変更しない）。
- SENT 以降は書き換えない。誤りは **取消（CANCELLED）→ 新しい番号で再発行**し、再発行側に元の請求書への参照を持つ（修正インボイス＝「当初交付分との関連性を明らかにして交付」）。
  - ★元の請求書への参照列は Invoice に無い → **`replacesInvoiceId`（仮名・nullable）を ADD COLUMN**（migration 1本・非破壊）。列名は実装ブリーフで確定。
- 取消した請求書に載っていた明細は、再び候補に戻る。

### 2-6. 入金（D-11）

- 請求書の詳細から「入金を記録」: 入金日・金額・方法（既定 銀行振込）・メモ → `Payment`（INCOMING・`PAY-{年}-{4桁}`）＋ `InvoicePayment`（充当額）。
- 請求書の `paidAmount` / `remainingAmount` / `isFullyPaid` と状態（PARTIALLY_PAID / PAID）を更新。一覧で未入金・一部入金・入金済みを出す。
- v1 は **1回の入金を1枚の請求書に充当**する形まで。1回の入金を複数の請求書に分ける消し込みは器（InvoicePayment が多対多）はあるが、画面は後段（★B番号は締めで起票）。
- 先の請求書（DEPOSIT）の入金もここで記録する（デポジットの着金確認）。

### 2-7. PDF（D-12）

- **納品書 PDF と請求書 PDF**を新設。B-086 の方式（プレビュー → 承認後ダウンロード）。発行者ブロック・宛先・明細の形（案A）をそろえる。
- 請求書 PDF の必須記載: 発行者名・登録番号・取引年月日（納品日）・内容・税率ごとの合計と税額・請求先名。先の請求・前受金の差し引きがある場合はその行も。
- 用紙は A4 縦の見込み（★実装ブリーフで確定）。

### 2-8. 締め（B-123・D-13〜D-16・D-21）

- **締めを記録する器は新しいモデル**（休眠モデルに該当なし・v0.1 §2-6）。1行 = 取引先の種類（クライアント／仕入先／工場／外注先）× 取引先 × 期間（開始日・終了日）× 状態（締め中／解除済み）× 締めた人・日時 × 解除した人・日時・理由。ADD TABLE（migration 1本・非破壊）。モデル名・列名は実装ブリーフで確定。
- 期間は各取引先の `closingDay` で区切る（Client / Supplier / Factory / Contractor とも既存列）。closingDay が空の取引先は月末締めとして扱う（★実装ブリーフで明記）。
- **ロックの判定**（締め中の期間に計上日が入る伝票）:
  - 納品書（計上日 = deliveryDate・取引先 = clientId）: 新規・編集・状態変更・論理削除を止める（D-21）
  - PO（計上日 = orderDate・取引先 = supplierId）／WO（計上日 = orderDate・取引先 = factoryId または contractorId）: 同上。★PO/WO には今 status による編集ガードが無い（v0.1 §2-6）ので、update / delete / status 変更 / create の各 action にロック判定を足す
  - 請求書: 締めた期間の請求書は取消もできない（解除してから）
  - 判定は **UI とサーバの両方**に置く（サーバ側が正）
- 締めは誰でも・解除は **UserRole が OWNER / ADMIN** だけ（D-15）。締め・解除とも AuditLog にも残す。
  - ★判定の軸は role（B-202 PR-4 と同じ）で、既存の tenantType（MASTER_ADMIN）軸とは別。★role を画面で変える手段は無い（B-205）→ 当面の管理者は seed の設定のまま。
- 締め後の変更の証跡（B-123 ノート §2 の3）: v1 は「解除中に AuditLog に残った変更」を解除の記録と並べて見られるところまで。専用レポートは後段。

### 2-9. 画面

- サイドバー「取引」に **請求（INV）**を足す（nav-items.ts:80-81 のコメントどおり）。一覧（未入金・一部入金・入金済み・取消のフィルタ）・新規（月次／先の請求）・詳細（送付済みにする・取消・再発行・入金を記録・PDF）。
- 締めの画面: 取引先ごとの期間の一覧（締め中／未締め／解除済み）と「締める」「解除する（管理者）」。置き場所は実装ブリーフで決める。
- クライアントの画面に `isQualifiedInvoiceIssuer`（先方が適格請求書発行事業者か）の入力を足す（Supplier には既にある）。
