## 2. 設計（v1.0 §2-4 を置き換える部分）

- v1.0 の「端数処理の向きは定数1か所」を、**クライアントごとの設定**に変える。
  - Client に端数処理の列を1本足す（値は 切り捨て／四捨五入／切り上げ・既定は切り捨て・NOT NULL DEFAULT）。**ADD COLUMN（非破壊）＝ migration 1本**。PR-2 の `replacesInvoiceId`（仮名）と同じ migration に入れてよい。
  - ★列名・enum 名は実装ブリーフで確定する。**その前に schema を実測し、休眠列・既存 enum が受け皿にならないかを当たる**（shunya-design-reread）。Supplier / Factory / Contractor には v1 では足さない（仕入 B-212 の仕様確認書で決める）。
- 請求書を作るとき、クライアントの端数処理を **Invoice にもスナップショット**するかは実装ブリーフで決める（発行後にマスターが変わっても、発行済みの税額は変わらない。税額そのものは `taxAmount10` 等に保存済みなので、スナップショットが無くても再計算しなければずれない）。
- クライアントの画面（新規・編集・詳細）に端数処理の入力を足す（v1.0 §2-9 の `isQualifiedInvoiceIssuer` と同じ場所）。
- 計算: 税率ごとに（課税対象額の合計 × 税率）を1回だけ、そのクライアントの向きで円未満を処理する。返品でマイナスになる場合の「切り捨て」の向き（0方向か、負の無限大方向か）は実装ブリーフで決める（★KKAP+ のマイナスの実例: ビームス 2026/08 は −765,000 → −76,500 で端数0のため参考にならない）。

### 2-2. 繰越型（D-24）の設計への影響（★たたき台・実装ブリーフの前に確定する）

- 計算: 今回御請求額 = 繰越金額 + 当月お買上げ額 + 消費税等。繰越金額 = 前回御請求額 − 御入金額。
  - 前回御請求額 = そのクライアントの直前の請求書（取消されていないもの）の今回御請求額。
  - 御入金額 = 前回の締め日の翌日〜今回の締め日に記録された入金（D-11・Payment INCOMING）の合計。
- 明細: 納品の明細に加えて「〔御入金〕振込」の行を入金日で並べる（KKAP+ の紙面どおり）。
- ★**入金（v1.0 の PR-5）が合計請求書（PR-2）の前提になる**。入金が記録できないと御入金額が常に 0 になり、繰越が膨らむ。→ PR の順番（PR-5 を前に出す／PR-2 に入金の記録を含める）は実装ブリーフの前に決める。
- ★**移行の初期値**: shunya-pms で最初に出す請求書の「前回御請求額」は、KKAP+ の直前の請求書の今回御請求額を人が入れる必要がある（クライアントごとの期首残高）。器（Invoice の列か別の記録か）は schema を実測して決める。
- ★Invoice に前回御請求額・御入金額・繰越金額の列があるかは未実測（v1.0 時点の実測にこの3つは無い）。無ければ ADD COLUMN（非破壊）。PR-2 の migration に入る。
- ★D-20（前受金の差し引き）との関係: 先に請求した分の入金は繰越の中で相殺される。差し引く行の扱いは K-1 と合わせて PR-3 の前に決める。
- ★当月お買上げ額が 0 でも繰越があれば請求書を出す（スタイルバンク東京 2026/08 の実例）。

### 2-3. schema 実測（2026-09-22 21:43 JST・Claude Code・read-only・main ac553df）

- Invoice（schema.prisma:6243-6396）: 前回御請求額・御入金額・繰越金額にあたる列は**無い**。入金状況は paidAmount(6349)・remainingAmount(6350)・isFullyPaid(6351)・fullyPaidAt(6352)。値引き discountAmount(6368)。
- Client（292-396）と既存 enum: **端数処理の列・値は無い**（grep round/端数/fraction のヒットは sampleRound・roundOrder のみ。繰越/前回/残高/balance は 0 件・陽性対照 closingDay 4 件）。
- Payment（6526-6621）: counterpartType(CounterpartType に CLIENT あり)・counterpartId・counterpartName を持ち、InvoicePayment を介さず単体で存在できる → **クライアント単位の入金（D-25）は既存の器のまま表せる**。paymentMethod は必須（PaymentMethod に BANK_TRANSFER あり）。scheduledDate 必須・actualPaymentDate 任意・status（PaymentStatus・既定 SCHEDULED）。relatedInvoiceIds(Json) あり。
- InvoicePayment（6660-6686）: invoiceId・paymentId とも必須。D-25 では v1 で使わない見込み。
- DDL: invoices / invoice_items / payments / invoice_payments の CREATE TABLE は 20260516075911_init のみ。以後 ALTER TABLE "invoices" / "payments" は 0 件（clients は2件）。src 実使用は4モデルとも 0 件（陽性対照 prisma.purchaseOrder. 21 件）。
- 税の端数処理の既存箇所: quotation-data.ts:227（Math.floor）／delivery-notes.ts:581（Math.round）。★請求書をクライアントごとの端数にすると、同じ取引先で納品書と請求書の税額が1円ずれ得る → 実装ブリーフで扱いを決める。
- enum TransactionType は schema に無い（Invoice.transactionType の型は InvoiceTransactionType・値は未取得）。

### 2-4. PR-2 に入る migration の見込み（すべて ADD・非破壊）

- Invoice: 前回御請求額・御入金額・繰越金額の3列＋再発行の元（replacesInvoiceId・v1.0 §2-5）。

### 2-5. 赤伝（D-26）の設計への影響（★たたき台・実装ブリーフの前に実測・確定する）

- 赤伝は納品書（DLV）の一種として持つ（新しいモデルは作らない見込み）。明細の数量をマイナスで入れる。
- ~~★未実測: 今の納品書が数量マイナスを許すか~~ → **2026-09-22 22:06 JST 実測（Claude Code・read-only・main ac553df）**:
  - DB: `DeliveryNoteItem.quantity` は Int（schema:6099・DDL `INTEGER NOT NULL`）、`unitPrice` は Decimal(15,2) nullable（6103）。delivery 系の CHECK 制約は 0 件（陽性対照: migration 全体で 3 件）→ **DB はマイナスを受け付ける**
  - validator: `src/lib/validators/delivery-note.ts:32` 数量は `Number.isInteger(v) && v > 0`、`:44` 単価は `v === null || v >= 0` → **マイナスを止めているのはここだけ**
  - action: `delivery-notes.ts` にマイナスを拒む・絶対値を取る処理は無い。小計 `Math.round(quantity × unitPrice)`（532-533）・税 `Math.round`（581）。★JS の Math.round は負数で 0 寄りに丸まらない（-0.5 → -0）ため、マイナス行の丸めは実装ブリーフで扱いを決める
