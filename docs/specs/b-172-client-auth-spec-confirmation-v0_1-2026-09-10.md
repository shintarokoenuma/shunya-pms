## 0. 本書の結論（先に4行）

1. **認証（ログイン済みか）は3系統で全経路が守られている。穴は無い。** ページに redirect が無いのは設計の帰結であり、脆弱性ではない（§1-1・§1-2）。
2. **認可（ログイン済みの誰に何を見せるか）は、物理削除ガードを除いて1行も存在しない。** role による分岐はコード全体でゼロ（§1-3）。
3. ★**ただし認可の要件は白紙ではない。原設計 §5.7 / §5.9 に開示・非開示のリストが確定済み**で、しかも「開示するものを列挙する」＝既定拒否＋ホワイトリストの形になっている（§2）。
4. ★**最大の論点は「認可レイヤーを B-172 専用に作るか、B-022（工場・仕入先・パタンナー開放）と共通の基盤として作るか」**である（§4 Q0）。原設計は社外3種を同じ枠で語っており、過去の spec も「ガードは B-022 と同時設計」と繰り返し申し送っている。

## 1. recon の実測（確定事実・調べ直し不要）

### 1-1. 認証は3系統。いずれも未セッションで拒否する

| 系統 | 実装 | 適用先 | 未セッション時 |
|---|---|---|---|
| A | withTenantContext（AsyncLocalStorage・companyId 自動付与） | clients / brands | throw "Unauthorized: no active session" |
| B | 各 action ファイルにローカル定義した requireSession() | products / sales-orders / materials / purchase-orders など約25ファイル | ok:false または throw |
| C | ★各 export の冒頭で await auth() を直書き | **suppliers / factories / contractors** | throw "認証が必要です" |

★C は requireSession の出現数が3ファイルとも 0 で、export 8個すべての直下に await auth() が並ぶことを行番号で確認済み。
★skus.ts:15 のコメント「house style: requireSession は各 action ファイルにローカル定義（共有 helper なし）」が B の方針を明文化している。
★buyers.ts:19 のコメントは「Contractor と同パターン（requireSession）」と書いているが、contractors.ts に requireSession は無い。**コメントが実装とずれている。**

### 1-2. ルート層に認証は無いが、穴にはなっていない

- ★**その10ページはいずれも prisma を直接触っていない**（陽性対照つきで実測。prisma を含む page.tsx は37件あり、その中に10ページは1つも含まれない）

## 2. ★原設計に既にある権限定義（仕様書 Part3 §5.7 / §5.9）

**本件は白紙からの設計ではない。** 2026-05-16 の原設計に次が確定している。

### 2-1. §5.7 クライアント開放の4パターン ＝ 進捗の表示レベル

| パターン | 内容 |
|---|---|
| A | 社内詳細10段階 |
| B | 簡略5段階 |
| C | 概要2段階 |
| D | 完全非開示 |

★**これは進捗ステータスの表示レベルであって、原価マスキングの器ではない。** ClientDisplayPattern（A/B/C/D・既定 B）が原価に使われていないのは実装漏れではなく、用途が別だったためである。原価の遮断は別の機構が要る。

### 2-2. §5.9 外注先（パタンナー）への情報共有範囲 ＝ 既定拒否の原型

| 開示する | 開示しない |
|---|---|
| 仕様書（担当案件のみ）／サンプル写真／修正指示／自分宛の WO（発注書）／工場情報・工場とのやり取り | ★**原価情報**／他のパタンナーの情報／他案件（担当外）／クライアントとの直接やり取り |

★**開示するものを列挙する形になっている＝原設計の時点で「既定拒否＋ホワイトリスト」の思想が採られている。** §4 Q2 の案は、この形を踏襲するのが原設計に忠実である。

### 2-3. §5.7 のその他（初版のスコープ判断が要る）

- 社内6階層（オーナー／管理者／生産管理／経理／営業／デザイナー）。★UserRole の8値との対応は未確認（§6）
- クライアントアクション: 問い合わせ入力／状況確認／見積もり承認／サンプル承認／仕様変更依頼
- 工場・仕入先開放: すべて開放可能・個別カスタム（仕様書／納期進捗確認依頼）
- アクセス制御3層: デフォルト（オーナー＋担当＋経理）／チーム／個別（機密案件）
- 編集競合制御: 同セクションはロック・別セクションは警告・ログは完全記録
- 認証の基本セキュリティ4項目: 強度ポリシー／履歴記録／不正検知／自動ログアウト

## 3. 実務側の確定事項（M-002・2026-09-08 慎太郎さん）

1. 専用オーダーページのアカウントは **クライアント企業に1つ（担当者で共有）**。担当者ごと・バイヤーごとではない
2. 1ページに載せる品番数は **固定しない（SKU 数によりフレキシブル）**
3. 先方に見せる UI は **SKU のマトリクス表**が最も馴染む（★品番カルテにも同じことが言える）
4. 先方に見せるのは現状 **品番・色・サイズ・数量まで**。卸値・納期・進捗は将来（現状不要）
5. ★納期は「**表示と現実は異なる**」＝先方向けの表示納期と社内の実納期が別物

★4 と §2-1 の関係: 進捗を現状見せない以上、**A/B/C/D の実装は初版では要らない**（既定 D 相当の運用）。§5 に送る。

## 4. 判断を仰ぐ論点

### Q0（★最大論点）認可レイヤーの器を、B-172 専用にするか B-022 と共通にするか

原設計 §5.7 / §5.9 は、社外を**クライアント／工場・仕入先／外注パタンナー**の3種として同じ枠で扱っている。
過去の spec にも「実際のガードは B-022（外部開放）と同時に設計する」「P7 権限ガードは v1 で実装しない（B-022 と同時設計）」という申し送りが複数回ある（BACKLOG_EVIDENCE B-022 節）。

| 案 | 内容 | 得失 |
|---|---|---|
| **案0-A** | 認可レイヤーを**社外共通の基盤**として設計し、B-172 はその第一適用（クライアント）とする | 二度作らない。原設計に忠実。★初版が重くなる |
| 案0-B | B-172 はクライアント専用に作り、B-022 で作り直す／拡張する | 初版が軽い。★同じものを二度設計する危険。過去に3回繰り延べた受注と同じ形 |

★Claude の見立て: 案0-A。ただし**「基盤を共通にする」と「初版で3種すべてを実装する」は別**で、器を共通にしたうえで初版の適用先をクライアントだけに絞ることはできる。判断は慎太郎さん。

### Q1 社外ユーザーはどう入るか

| 案 | 内容 | 影響 |
|---|---|---|
| 案1-A | **User を作る**（UserRole.EXTERNAL を起こす）＋ User → Client の参照列を新設 | schema 変更あり（列1本・非破壊）。社内と同じ認証系に乗る。監査ログが効く |
| 案1-B | **User を作らない。** OrderPage の accessType（PASSWORD_PROTECTED / LINK_ONLY）＋ restrictedBuyers で入れる | schema 変更なし（器は既存）。★誰が入力したかが残らない。パスワード共有の運用になる |
| 案1-C | 併用（初版は 1-B、将来 1-A） | 二度作る |

★M-002 の「クライアント企業で1アカウント共有」は 1-A でも 1-B でも実現できる。**1-A なら「企業に1つの User」、1-B なら「ページにパスワード1つ」。**
★受注は数量の正になるため、**誰が入力したかを残す必要があるか**が判断の分かれ目。

### Q2 認可をどう効かせるか（認証3系統への適用）

| 案 | 内容 | 得失 |
|---|---|---|
| **案2-A** | 既定拒否＋ホワイトリスト（社外が呼べる action / ルートを列挙し、それ以外は一律拒否） | ★原設計 §5.9 と同型。穴が残りにくい。列挙の初期コストが要る |
| 案2-B | ブラックリスト（原価に触れる action を個別に塞ぐ） | 着手は軽い。★原価語を含む src ファイルは38件あり、1つ漏れると漏洩する |

★どちらを採っても、**3系統すべてに効かせる必要がある。** 系統 C（suppliers / factories / contractors）は**仕入先・工場そのもの**＝原設計が「絶対に見せない」と定めた対象なので、ここを外すと目的を達しない。
★共通フックの置き場所の案: ①withTenantContext に一本化する（B と C を書き換える大手術）②3系統が共通で呼ぶ薄い認可関数を新設する ③middleware.ts でルート層に敷く（ページは通しても action は通るため単独では不十分）。**この3案の選択は Q0 の答えに依存するため、v1.0 で確定させる。**

### Q3 ClientDisplayPattern（A/B/C/D）の役割を確定させる

§2-1 のとおり原設計では進捗の表示レベルである。

- 案3-A: 原設計どおり**進捗専用**とし、原価の遮断は別機構にする（★Claude の見立て）
- 案3-B: 原価・卸値も含む総合的な開示レベルに拡張する

### Q4 UserRole.EXTERNAL と User.isExternalUser を使うか

どちらも器だけ在って未使用。Q1 が案1-A なら起こすことになる。
★role 軸（ユーザーの役割）と tenantType 軸（会社の種別）のどちらを認可の主キーにするかを、ここで決める。既存の唯一の認可（物理削除ガード）は **tenantType 軸**である。

### Q5 OrderPage.productId 必須（1ページ1品番）をどうするか

M-002 の 2（フレキシブル）および実オーダーシート1通20品番（addendum §0）と食い違う。

- 案5-A: productId を nullable 化し、ページ配下に品番の集合を持たせる（SalesOrder.productId で同型の訂正を実施済み）
- 案5-B: 1ページ1品番のまま、複数ページをまとめて見せる導線を作る

★これは B-171 の設計だが、**認可の単位（何を1つの開放単位とするか）に直結する**ため本書で決める。

### Q6 初版のスコープ

- 案6-A: B-171 が動くのに必要な最小限（クライアントの受注入力に必要な範囲だけ開放）
- 案6-B: 原設計 §5.7 のクライアントアクション5つ（問い合わせ／状況確認／見積承認／サンプル承認／仕様変更依頼）まで含める

★M-002 の 4（卸値・納期・進捗は現状不要）は案6-A を支持する。
