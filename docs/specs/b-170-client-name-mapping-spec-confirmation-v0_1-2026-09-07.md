## 0. 本書の結論を先に3行

1. ①品番の対応表は **新テーブルを建てなくてよい可能性が高い**。Product.clientProductCode と Product.clientId（必須）が既に「品番×クライアント」を表している。
2. ②色名の対応表は **クライアント方向の器が schema に1つも無い**。ここだけが新規に必要な構造である。
3. ★**表記ゆれを吸収する照合が要るのは B-149（Excel 取込）だけ**で、本命の B-171（専用オーダーページ）には要らない。この切り分けで B-170 の必須範囲は小さくなる。

## 3. ★本書の中心となる切り分け（先に決めたい）

addendum §1 は「名寄せ基盤は B-171 / B-149 の共通の土台」と書いている。これは正しいが、**共通なのは一部だけ**である。

| 機能 | B-171 専用オーダーページ（本命） | B-149 Excel 取込（移行期） |
|---|---|---|
| 先方品番を**表示**する | **要る**（先方の画面に先方のコードが並ばないと使えない） | 要る（取込結果の確認画面） |
| 先方色名を**表示**する | **要る** | 要る |
| 先方コードの文字列を**照合**する | ★**要らない**（先方は一覧から選ぶ。文字列は発生しない） | **要る**（シートの文字列を当てにいく） |
| 表記ゆれ（桁数・前ゼロ・英字大小）の吸収 | ★**要らない** | **要る** |
| 対応が付かない行の突き合わせ画面 | 原則発生しない | **要る** |

**決めたいこと**: B-170 の必須スコープを「**保持と表示**」に絞り、「**照合と突き合わせ**」を B-149 側に寄せるか。

- 案X: B-170 = 保持と表示のみ。照合・正規化・突き合わせ画面は B-149 のスコープに移す
  - 利点: B-170 が小さくなり、B-172 → B-171 の本命ラインに早く着ける
  - 欠点: B-149 が重くなる
- 案Y: addendum の記述どおり、照合・突き合わせ画面まで B-170 に含める
  - 利点: 出典どおり。B-149 が軽くなる
  - 欠点: 本命ラインの手前に、本命では使わない機能を作ることになる

★Claude はどちらが正しいとも言わない。判断材料のみ記す。

## 4. 論点1 — ①品番×クライアントの対応表

### 4-1. addendum の記述の解釈

addendum §1 は「品番×クライアントの対応表と色名の対応表を**分けて持つ**設計とする」と書いている。

この文の文脈は「Sku.clientSkuCode の SKU 単位（179行分の登録が必要）は粒度が細かすぎる」への反論であり、趣旨は **粒度を分けろ**（品番単位と色単位に分ける）である。**「新テーブルを2本建てよ」と読むかは解釈の余地がある。**

### 4-2. 選択肢

- **案1-A: 新テーブルを建てない。** Product.clientProductCode を先方品番の正とする
  - 根拠: Product.clientId が必須 ＝ 1品番は1クライアントに属する。したがって Product の行そのものが「品番×クライアント」の対応である
  - 実務の裏付け: 先方品番は1品番に1種（§2-1）
- **案1-B: 新テーブル（clientId × productId × 先方コード）を建てる**
  - 必要になるのは「**同一の自社品番を複数クライアントに出す**」場合のみ

### 4-3. ★決めていただきたいこと（Q1）

**同一の自社品番を、複数のクライアントに出すことはありますか。**

「先方品番は1種」というお答えは「1クライアントにつき1種」の意と解しましたが、**1品番が複数クライアントにまたがるか**は未確認です。無いなら案1-A で確定できます。

## 5. 論点2 — ②色名の対応表（★新規の器が必要なのはここだけ）

### 5-1. 確定している前提

- クライアント方向の色名を受ける列は **schema に1つも無い**（§1）
- 自社側の正は Color マスター（colorNumber 2桁）。クライアント色マスターは作らない（§2-2）
- 実データの先方色名には **複合色名**がある（addendum §0「BLACK×襟BLUEDENIM」）。これは Color の単色1つに対応せず、**品番固有の配色**である

### 5-2. 選択肢

- **案2-A: ProductColorway に先方色名の列を1本追加する**
  - 粒度: 品番 × 配色。複合色名（BLACK×襟BLUEDENIM）をそのまま受けられる
  - Product.clientId が必須 ＝ 品番は1クライアント専用 ＝ その配下の配色も1クライアント専用なので、クライアント別に分ける必要がない
  - **BomItemColorway が仕入先方向で採っている形（カラーウェイ単位に外部コード／名を持つ）と同型**。既存の実装思想と揃う
- **案2-B: クライアント × 色名 の中間テーブル（先方色名の辞書）**
  - 先方色名が品番横断で再利用される前提が要る
  - ★複合色名を扱えない。BLACK×襟BLUEDENIM は品番固有であり辞書に載らない
- **案2-C: Client × ProductColorway の中間テーブル**
  - 同じ配色をクライアントごとに別名で呼ぶ場合に要る
  - Product.clientId が必須である以上、冗長になる

### 5-3. ★決めていただきたいこと（Q2・Q3）

**Q2: 案2-A / 2-B / 2-C のどれで進めますか。**（実測は 2-A を支持しますが、判断は慎太郎さんです）

**Q3: 先方の「色コード」も要りますか、「色名」だけでよいですか。**

仕入先方向は supplierColorCode が**必須**・supplierColorName が任意という非対称です。一方、実オーダーシートには色**名**しかありませんでした。クライアント方向は名のみでよいか、コード欄も持つかで列数が変わります。

## 6. 論点3 — ③対応が付かない行の突き合わせ画面

### 6-1. 選択肢

- **案3-A: 品番カルテのカラーウェイセクションに、先方表記の入力欄を足す**
  - 品番は季ごとに新規発生する。新品番のたびに一度登録すれば、以後は安定する
  - 既存の colorway-section.tsx に載る（ProductColorway は現役・10ファイルで使用中）
  - 名寄せを「取込のたびの作業」ではなく「品番登録時の作業」に前倒しできる
- **案3-B: 取込画面（B-149）の中で、当たらなかった行だけを人が紐づける**
  - 救済としては必要。ただし単独だと毎回発生する
- **案3-C: 独立した「名寄せ」画面（クライアント別に未対応行を一覧）**
  - 件数が増えてから。初版では過剰の可能性

**3-A を主・3-B を従の2段構えでよいですか。**（3-C は将来の拡張として繰り延べ、B番号を振る）
