## 0. 結論（先に5行）

1. **認可の器は社外共通**（Q0=案0-A）。初版の適用先はクライアントのみ。工場・仕入先・外注パタンナーは B-022 で適用を足す
2. **社外ユーザーは User を作る**（Q1=案1-A）。`UserRole.EXTERNAL` を起こし、`User → Client` の参照列を新設する
3. ★**社外 User は shunya テナントの中に置く**（Q4=案4-A）ため、**テナント分離は壁にならない。既定拒否の認可が唯一の壁になる**
4. **ホワイトリストは「自社のオーダー」だけ**（Q2=案2-A）。見せるのは 先方品番・絵型・色・サイズ・数量・**売値・納期**
5. ★**売値の正は量産見積（ProductionEstimate）の提示1枚単価**。最終請求は実績原価ベースで、**提示と請求は一致しない前提**の業務である（M-006）

## 1. 確定事項

### D-1 認可の器は社外共通とする（Q0=案0-A）

認可レイヤーを社外共通の基盤として設計し、B-172 をその第一適用（クライアント）とする。
工場・仕入先・外注パタンナーへの適用は B-022 で「適用を足す」形にする。

- 根拠: 原設計 §5.7 / §5.9 が社外3種を同じ枠で扱っている。過去の spec も「ガードは B-022 と同時設計」と複数回申し送っている
- ★「器を共通にする」と「初版で3種すべてを実装する」は別。**初版の適用先はクライアントのみ**

### D-2 社外ユーザーは User を作る（Q1=案1-A）

- `UserRole.EXTERNAL`（既存・src 参照ゼロの休眠値）を起こす
- `User` に Client への参照列を新設する（ADD COLUMN 1本・nullable・非破壊）
- アカウントの単位は **クライアント企業に1つ（担当者で共有）**（M-002 の1）
- 却下した案: OrderPage の password / restrictedBuyers だけで入れる方式（案1-B）。
  ★理由は**誰が入力したかが残らない**こと。受注は数量の正（B-168 で SO 由来に一本化済み）であり、入力者が追えない状態で数量の正を預けられない
- ★副産物: `User` には `failedLoginAttempts` / `lockedUntil` / `passwordChangedAt` と `UserLoginHistory[]` が実在するため、B-199（認証の基本セキュリティ4項目）の器にそのまま乗る

### D-3 所属テナントと、認可の主キー（Q4=案4-A）

- 社外 User は **shunya テナントの中**（`companyId` = shunya）に置く
- `role = EXTERNAL` ＋ 新設の clientId 参照で「自社のオーダーだけ」に絞る
- ★**認可の主キーは role 軸**とする。既存の唯一の認可（物理削除ガード）は tenantType 軸だが、社外 User を同一テナントに置く以上 tenantType では区別できない
- ★**最重要の帰結**: テナント分離（AsyncLocalStorage による companyId 自動付与）は社外に対して**壁にならない**。
  D-4 の既定拒否が唯一の壁である。**穴が1つ空くと原価まで届く**
- 却下した案: クライアントごとに Company（テナント）を作る（案4-B）。
  ★理由は、自社の受注（shunya テナントにある SalesOrder）を読むための越境経路を新設することになり、テナント分離の原則に自分で穴を開ける方向になるため

### D-4 認可は既定拒否＋ホワイトリスト（Q2=案2-A）

- 社外セッション（`role = EXTERNAL`）は**既定で全拒否**とし、許可するものだけを列挙する
- 許可する範囲は「**自社のオーダー（受注）**」のみ（M-004 の原文「社外ユーザーがログインして確認できるのはオーダー内容だけ」）
- 却下した案: 原価に触れる action を個別に塞ぐブラックリスト（案2-B）。
  ★理由は RECON-J の実測で**原価が出る面が38ファイル**あり、うち **lib/pdf が5件**＝PDF 出力にも原価が乗るため。ページと action だけを塞ぐ設計では漏れる
- ★共通フックの置き場所は「**3系統（withTenantContext / 各ファイルの requireSession / 各 export の await auth() 直書き）が共通で呼ぶ薄い認可関数を新設する**」とする。
  系統 C（suppliers / factories / contractors）は原設計が「絶対に見せない」と定めた対象そのものなので、ここを外すと目的を達しない

### D-5 ★ホワイトリストの中身（社外に見せるもの／見せないもの）

| 見せる | 出所 | 備考 |
|---|---|---|
| 先方品番 | `Product.clientProductCode` | B-170 で実装済み（RECON-K 実測） |
| 絵型 | `Product.sketchImages`（Json）/ `sketchThumbPath` | 既存 UI は `sketch-section.tsx` |
| 色（先方色名） | `ProductColorway.clientColorName` | B-170 で実装済み・migration `20260908000000_b170_product_colorway_client_color_name` |
| サイズ | `Sku.size` | |
| 数量 | SKU マトリクス表で先方が入力する | 既存実装 `quantity-matrix-section.tsx` / `color-quantity-section.tsx` を流用元とする |
| ★売値 | **量産見積（ProductionEstimate）の提示1枚単価**（D-9） | shunya が事前に設定。先方は数量だけ入れる |
| ★納期 | **表示納期**（D-10） | 社内の実納期とは別物 |

| 見せない | 理由 |
|---|---|
| 原価（1枚原価・材料費・工賃） | 原設計 §5.9 の非開示リスト筆頭 |
| 仕入先・工場 | 同上 |
| 利益率・マージン | 同上 |
| 進捗 | M-002 の3（現状不要）。実装は B-197（表示レベル A/B/C/D） |
| 他クライアントの一切 | clientId で絞る（D-3） |

★**この表が D-4 のホワイトリストの実体である。**これ以外は既定拒否。

### D-6 オーダーページは1ページ複数品番とする（Q5=案5-A）

- `OrderPage.productId` を nullable 化する（DROP NOT NULL・非破壊）。前例は `SalesOrder.productId`（B-148・受注 spec v1.0 §0 の訂正）
- 1ページに複数品番を載せ、**1品番あたり1ブロック = 先方品番 / 絵型 / SKU マトリクス表**を最低限表示する（M-004 の原文）
- 根拠: M-002 の2（1ページの品番数は固定しない）・実オーダーシート1通20品番（sales-order-spec-addendum §0）
- ★ページ配下に品番の集合をどう持つか（子テーブル新設か、受注期間単位か）は **B-171 の設計**に委ねる。本書は粒度の方針だけを決める

### D-7 ClientDisplayPattern は進捗専用のまま（Q3=案3-A）

原設計 §5.7 の A/B/C/D は**進捗ステータスの表示レベル**であり、原価マスキングの器ではない。
原価の遮断は D-4 の既定拒否が担う。A/B/C/D の実装は **B-197**。

### D-8 初版スコープは受注入力に必要な最小限（Q6=案6-A）

クライアントアクション5つ（問い合わせ入力／状況確認／見積承認／サンプル承認／仕様変更依頼）は **B-198** のまま。

### D-9 ★売値の正は量産見積の提示1枚単価（M-006）

- 先方ページに出す売値は **ProductionEstimate の「提示1枚単価」と紐付ける**。新しい価格マスターは作らない
- ★**確定見積（`Quotation` / QE-2 / B-143）は使わない。**よって **B-171 の着手は B-143 を待たない**
- 二層構造（M-003）の上に載る: 原価（社内）は 総額 ÷ 数量、提示（客向け）は 1枚単価 × 数量。先方に出すのは後者
- ★**最終請求は「量産実績原価（発注後・材料費＋工賃）」を基礎にする**（M-006 の原文）。
  提示（見積ベース）と請求（実績ベース）は**一致しない前提**である。
  ★ただし「実績原価になる」の意味（実績原価そのものか／マージンを乗せるか／見積を改訂するか）は**未確定**。§4-1 に置く

### D-10 ★納期は「表示納期」である（M-004・M-002 の5）

先方に出す納期は**表示納期**であり、社内の実納期とは別物（M-002 の5「表示と現実は異なる」）。
★M-002 の5 は「将来」として B-171 の定義欄に畳んでいたが、**納期を初版で出すため格上げになった**。
別の列として持つか同じ列を出すかは §4-1 の未確定。

## 2. 実測の根拠（要点。全数の内訳は addendum v0.1 §2）

### 2-1. 認証は3系統。穴は無い

A: withTenantContext（clients / brands）／B: 各ファイルにローカル定義した requireSession（約25ファイル）／
C: 各 export の冒頭で await auth() 直書き（suppliers / factories / contractors）。いずれも未セッションで拒否する。
(app) 配下の page.tsx 93 のうち auth を import しない10ページは、**いずれも prisma を直接触っていない**（陽性対照37件つきで実測）。

### 2-2. 認可は物理削除ガードを除いて存在しない

- MASTER_ADMIN **90件**（.ts 46 は全行目視・実行判定20箇所はすべて tenantType 比較／.tsx 44 は本文未目視）
- `session.user.role` の実使用は **6件**で、全行が配線と表示。**分岐はゼロ**（陽性対照: tenantType は102件）
- `runWithoutTenantContext` は **42ヒット**（実呼び出し19件はすべて `delete◯◯Permanently` の内側）＝バイパスは物理削除専用
- 原価系 action（production-cost / production-estimates / rough-estimates）は role 0件・displayPattern 0件。**認証さえ通れば誰でも原価を取得できる**

### 2-3. 器の状況

| 器 | 状態 |
|---|---|
| `UserRole` | 8値（OWNER/ADMIN/PRODUCTION/ACCOUNTING/SALES/DESIGNER/STAFF/EXTERNAL） |
| `User` → client / supplier / factory / buyer | ★**参照列なし**（全文確認）→ D-2 で新設する |
| `User` のセキュリティ列 | failedLoginAttempts / lockedUntil / passwordChangedAt / UserLoginHistory[] が**実在** |
| `OrderPage` | schema 完全定義・**src 実装ゼロの休眠**。必須列は `productId` のみ |
| `Client` | `displayPattern`（既定 B）実在。`@@unique([companyId, clientCode])` |

### 2-4. ★RECON-K（2026-09-10・本書のための実測）

- **B-170 は実装済み**: `ProductColorway.clientColorName` が schema に実在（「先方色名（B-170）」コメント付き）／migration `20260908000000_b170_product_colorway_client_color_name` が存在／src 3ファイルで14ヒット（colorway-section.tsx / product-colorways.ts / product-colorway.ts）。`Product.clientProductCode` の src 参照は59件
- **絵型**: `Product.sketchImages`（Json）/ `sketchThumbPath`。UI は `sketch-section.tsx`。★`DesignVersion.flatSketchFrontUrl/BackUrl` とは別レイヤー
- **SKU マトリクス**: `quantity-matrix-section.tsx` / `color-quantity-section.tsx` が既存（流用元）
- ★**BACKLOG の B-170 の状態欄が実態と食い違っていた**（実装済みなのに記載が更新されていなかった）。本書と同じコミットで訂正する

## 3. 実装の骨子（実装ブリーフで詳細化する）

### 3-1 schema 変更（3点・すべて非破壊）

1. `User` に Client への参照列を追加（nullable・scalar FK＝house style・`@relation` なし・`companyId` との複合 index）
2. `OrderPage.productId` を DROP NOT NULL
3. `UserRole.EXTERNAL` は既存値なので **enum の変更は不要**

★ページ配下の品番集合（子テーブル）は **B-171 のスコープ**。本書では作らない。

### 3-2 認可関数（新設）

- 3系統すべてが共通で呼ぶ薄い関数を1本新設する
- `role = EXTERNAL` を**最上位の関門**にする（既定拒否）。許可は D-5 の表に列挙したものだけ
- 社外セッションで許可外の action を呼んだら拒否し、**AuditLog に記録する**（プロジェクトの鉄則6）

### 3-3 画面

- 先方向けページを `(app)` 配下に置くか外に置くかは**未確定**（§4-1）。`(app)/layout.tsx` は AppShell（社内ナビ）を被せるため、社外にそのまま見せる前提になっていない

## 7. migration 運用（shunya-environment-safety-check ルール00）

`prisma migrate dev` は**使わない**（dev に `_prisma_migrations` が無く DB 全体の reset を要求する）。
正運用: `migrate diff` のドライラン → `db push` → **手書き** migration → `migrate diff` の出力と手書きの一致検証 → 本番は Railway の `migrate deploy`。
`prisma migrate reset` と `--accept-data-loss` は実行も提案もしない。
