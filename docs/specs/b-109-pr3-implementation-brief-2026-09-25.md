## §1 金額の流れ（受注 税抜 1,000,000・前受金 40%）

| 時点 | 伝票の行 | 請求書 |
|---|---|---|
| 前受金を請求 | 前受金の伝票（納品完了）「前受金（SO-○○）」数量 1・単価 400,000 | 400,000 ＋ 税 40,000 ＝ 440,000 |
| 入金 | クライアント単位で 440,000（今のまま） | 次の請求書の御入金額で相殺 |
| 納品 | 品番の明細 全額 1,000,000 ＋「前受金充当（SO-○○）」数量 −1・単価 400,000 | 600,000 ＋ 税 60,000 ＝ 660,000 |

★税は請求書1枚につき税率ごとに1回（D-22）のまま。前受金の行も充当の行も 10% の課税行として扱う。

## §2 確定事項

- **P3-D1 行の印**: `DeliveryNoteItem` に `lineKind`（nullable）を足す。enum は2値 `DEPOSIT`（前受金）/ `DEPOSIT_APPLIED`（前受金充当）。**null＝通常の行**（既存の全行は null のまま）。enum 名・列名は着手時に `grep -n '^enum ' prisma/schema.prisma` で重複が無いことを確かめて確定する（第一案 `DeliveryLineKind` / `line_kind`）
- **P3-D2 前受金の行の形**: `lineKind=DEPOSIT`・`soId=受注の id`・**`soItemId` と `skuId` は null**（納品済み数に混ざらない）・`productId`＝その受注の最初の明細の品番（品番必須のため）・品名「前受金（SO-○○）」・数量 **1**・単位「式」・単価＝前受金額
- **P3-D3 充当の行の形**: `lineKind=DEPOSIT_APPLIED`・`soId=受注の id`・`soItemId` と `skuId` は null・品番は P3-D2 と同じ・品名「前受金充当（SO-○○）」・数量 **−1**・単価＝充当額
- **P3-D4 入力チェック（サーバが正）**: `lineKind` がある行は `soId` 必須・`soItemId` と `skuId` は禁止。DEPOSIT は数量 1、DEPOSIT_APPLIED は数量 −1。単価は 1 以上の整数。**充当額の合計はその受注の未充当額を超えない**（編集時は自分の納品書の行を除いて計算）。★UI で隠すだけでなく validator と action の両方で判定する
- **P3-D5 前受金の集計（1か所に置く）**: 受注ごとに「請求済み＝DEPOSIT 行の金額の合計」「充当済み＝DEPOSIT_APPLIED 行の金額の絶対値の合計」「残り＝請求済み − 充当済み」。対象は論理削除されていない・取消（CANCELLED）でない納品書の行（状態は問わない＝下書きの充当行も充当済みに数える。二重に充当させないため）。★この集計は `src/lib/billing/` に純関数＋読み取り関数として1か所に置き、受注画面・納品書・請求書の3か所から使う
- **P3-D6 受注の画面「前受金を請求」**:
  - 出す条件: 受注のクライアントの取引条件が `DEPOSIT_COD` または `ADVANCE_PAYMENT`、かつ受注が取消でない
  - ダイアログ: 金額（初期値＝受注の税抜額 `subtotal` × 前受金%・円未満切り捨て。`ADVANCE_PAYMENT` は 100%）・日付（初期値＝今日）→「前受金を請求する」
  - 保存すると、P3-D2 の行1つを持つ納品書が**納品完了（DELIVERED）**で1枚できる（`primarySoId`＝受注・`clientId`＝受注のクライアント・納品日＝入れた日付）。★出荷元・出荷先など NOT NULL の列は、既存の納品書の作成処理と同じ埋め方をする（新しい作り方を作らない）。AuditLog に残す
  - 受注の画面に「前受金」の節: 請求済み／充当済み／残り と、前受金の伝票・充当の行がある納品書へのリンク
- **P3-D7 納品書での充当の提案（入れ忘れ防止①）**: 納品書の作成・編集で、明細にある受注（soId）に未充当の前受金が残っていれば、明細の上に黄色の枠で「SO-○○ に充当していない前受金 ¥400,000 があります」と「充当の行を入れる」ボタンを出す。押すと P3-D3 の行が入る（単価＝残り・人が減らせる）。★保存は止めない
- **P3-D8 請求書での警告（入れ忘れ防止②）**: 請求書の作成画面で、候補の明細に受注の行（soItemId あり）があり、その受注に未充当の前受金が残っていれば「SO-○○ の前受金 ¥400,000 がまだ充当されていません。この請求書に載る納品書に「前受金充当」の行を入れてください。」を出す。★保存は止めない（B-223 の警告と同じ扱い）
- **P3-D9 表示**: 納品書の一覧・詳細で、前受金の行を持つ納品書に「前受金」のバッジ、明細の行に「前受金」「前受金充当」のバッジ。請求書の明細は品名がそのまま写るので追加の変更なし
- **P3-D10 編集で印を落とさない**: 納品書の下書きの編集は明細を作り直す（B-124）。`lineKind` と `soId` が作り直しでも保たれることを確かめる。前受金の伝票（DEPOSIT 行を持つ納品書）はフォームで編集させない（取消して作り直す）
- **P3-D11 今回やらないこと**:
  - `InvoiceType.DEPOSIT`・入金と請求書の紐づけ（`InvoicePayment` / `relatedInvoiceIds`・D-25 のまま）
  - 代引き（CASH_ON_DELIVERY）の前受金（代引きは納品時の支払いなので前受金は無い）
  - 受注の取消・減額で前受金が余ったときの返金・精算 → ★締めで BACKLOG を grep してから起票する
  - 前受金の伝票の PDF の見せ方 → PR-4 で扱う
  - 請求書の新規作成画面への受注からの直接リンク（期間の自動入力）

## §4 migration の手順（shunya-pms の正運用・`prisma migrate dev` は使わない）

1. `.env` の DATABASE_URL が dev（hopper.proxy.rlwy.net:12921）であることを確かめる
2. schema を編集 → `npx prisma migrate diff --from-schema-datasource prisma/schema.prisma --to-schema-datamodel prisma/schema.prisma --script` で SQL を表示（ドライラン）。CREATE TYPE 1つと ALTER TABLE ADD COLUMN 1つだけであること
3. `npx prisma db push`（dev に反映）。★data loss の警告が出たら止める
4. `prisma/migrations/` の最新フォルダ名を確かめ、それより後に並ぶ名前で新しいフォルダを作り、2 の SQL を `migration.sql` に書く
5. もう一度 2 を実行し、差分が空であることを確かめる
6. `npx prisma generate` → dev サーバを再起動（起動中の next dev は古い Client を掴む）
- ★`prisma migrate reset` と `--accept-data-loss` は使わない

## §7 本番への影響

migration（ADD COLUMN nullable＋enum 1つ）がマージ時に本番へ当たる。既存の納品書明細はすべて null（通常の行）のままで、表示・計算は変わらない。前受金の機能は、取引条件が「デポジット＋COD」か「前払い」のクライアントの受注にだけ出る。コードは revert で戻せるが、列と enum は残る（空のまま害は無い）。
