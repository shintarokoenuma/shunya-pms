## 0. この追補が生まれた根拠（実データ）

クライアント1社の1シーズン分オーダーシートを実物で確認した。

- 1通 = 20品番・明細179行・総数量1301点・小計 10,468,500 円
- 変更があるとシート全体が再送される（差分ではなく全面差し替え）
- 単価は品番内で完全に一律（例: 26S-JK01 は全9行 17,200 円）
- 受注数 0 の行は存在しない（受注のある SKU のみ記載）
- 発注No 欄が空欄
- 表記の揺れ: サイズ欄に「M：サンプル」の注記／色名が複合（BLACK×襟BLUEDENIM）
- ★このシートには計算誤りがある。小計10,468,500 に対し「消費税」欄が 11,515,350
  （= 税込額）、合計が 21,983,850（税抜と税込の二重計上）。正しくは消費税1,046,850・
  合計11,515,350。先方提示額を信用してはいけないことの実証。

## 1. R-10 の改訂 — 入力経路は3層構造

### v1.0 の記述（置換対象）

「手入力1系統。sourceType・originalFiles は初版から保持。自動読取は B-149」

### 改訂後

入力経路を次の3層とする。出口はすべて SalesOrder（R-4 のまま不変）。

| 層 | 経路 | 位置づけ | B番号 |
|---|---|---|---|
| 本命 | 専用オーダーページ（先方が入力） | 今後クライアントに依頼していく主経路 | B-171 |
| 移行期 | Excel 取込 | 移行期および専用ページに対応できないクライアント用 | B-149 |
| 恒久 | 手入力 | 電話・チャット・イレギュラーの代打ち。★恒久的に残す | PR-1 で完成 |

★方針転換の理由: オーダーシートの様式がクライアントごとに全て異なるため、
取込のパーサーはクライアント数だけ必要になる。入口を揃えるほうが安い。
★ただし全クライアントが一斉に移行することはないため、3層は並走する。
　v1.0 R-10 の「専用ページを将来作っても代打ちは必ず必要」という判断は今も正しい。

### 名寄せ基盤は全経路の共通前提（新規）

先方の商品コード（26S-JK01）と自社品番（AOI-26SS-M-TS-001）は別体系で、
現在は人が突き合わせている。

★専用オーダーページにしても名寄せは消えない。先方の画面には先方の商品コードが
　並んでいないと使えないため。よって名寄せ基盤は B-171 / B-149 の共通の土台となる（B-170）。

  B-170 名寄せ基盤
     ↓
  B-172 クライアント認証・権限 → B-171 専用オーダーページ
                              → B-149 Excel 取込

★Sku.clientSkuCode は既存列だが SKU 単位では粒度が細かすぎる（179行分の登録が必要）。
　実データの先方コードは品番単位で、色とサイズは別列。
　品番×クライアントの対応表と色名の対応表を分けて持つ設計とする（詳細は B-170）。

## 2. R-11 の改訂 — 同一品番の重複は検知＋警告

### v1.0 の記述（置換対象）

「入力は受注一覧に一本化。品番カルテは品番軸の集約表示」

### 改訂後

入力の一本化・カルテの集約表示は不変。これに次を追加する。

- 同一品番が複数の有効な SO に現れることを、DB の一意制約では禁止しない
- 作成・編集時に検知し、既存 SO の番号と数量を示して人に選ばせる
  - 「差し替え（再送されたオーダーシートの反映）」
  - 「リピート（別納期の追加生産）」

★一意制約にできない理由: リピートは正当な業務。同一品番が再度発注されることがあり、
　その場合は納期が異なるため別 SO になる（慎太郎さん確認 2026-08-19）。
　制約で禁止すると正当なリピートが弾かれる。

★「1品番1SO」は採らない。実データの1通=20品番を分割すると、再送のたびに
　20件を開いて突き合わせることになる。SO = 先方の発注1通（R-5）を維持する。

## 3. カルテの受注セクションの導線（新規）

現状はカルテの受注セクションに「受注を作成」が目立つ位置にある。
既に紐づく SO があるのに新規作成が主導線になっているのは誤り。

- 既存の紐づく伝票の編集リンクを主とする
- 「受注を作成」は従とし、既に紐づく SO がある場合は確認を挟む
- ★SO の単位そのもの（R-5）は変えない

## 4. 単価の扱いの改訂

v1.0 および実装ブリーフ D-2 の「品番単位で1つ入力し全 SKU に配る」は
実データで裏付けられた（品番内の単価は完全に一律）。これは不変。

これに次を追加する。

- SoItem.unitPrice を nullable 化する（migration 1本・DROP NOT NULL・非破壊）
- 理由: 希望数量の段階では最終コストが出ていないことが実務上ある
  （数量明細が先に来て、単価は後から確定する）
- 0 と「未定」を区別できるようにしたうえで、0 は異常値として警告する
- 明細から再計算した金額と先方提示額が乖離する場合に警告する
  ★§0 のとおり、先方シートには実際に計算誤りがあった
