## 2. 確定事項

### 2.1 サイドバー構成（最終版）

```
【業務メイン】
  ├─ ダッシュボード
  ├─ 案件
  │   ├─ サンプル        ← 進行中のサンプル一覧
  │   └─ 量産            ← 進行中の量産一覧
  └─ 問い合わせ（INQ）

【伝票】※ 品番・ブランドで検索可能
  ├─ 見積（QT）
  ├─ 発注（PO/WO）
  ├─ 受注（SO）
  ├─ 納品（DLV）
  └─ 請求（INV）

【マスター - クライアント側】
  └─ クライアント
      ├─ ブランド
      ├─ バイヤー
      └─ 納品先

【マスター - 仕入先側】
  ├─ 仕入先
  └─ 工場
      ├─ 外注
      └─ 諸経費

【マスター - その他】
  ├─ モデルコード
  ├─ 商品カテゴリ
  └─ 素材

【設定 / 管理】
  ├─ ユーザー管理
  ├─ 為替レート
  └─ 監査ログ
```

### 2.2 表記ルール

| 項目 | 表記 | データモデル上の対応 |
|---|---|---|
| 業務メインの最上位 | 「案件」 | `Product`（品番カルテ） |
| サンプル/量産の表示方法 | サイドバーで別メニュー | `Product.status` によるフィルタ |
| 伝票系の位置 | 業務メインと別グループ | QT / PO / WO / SO / INV / DLV |
| マスターのグルーピング | 3 グループ（クライアント側 / 仕入先側 / その他） | データ的には独立、表示上の階層化 |

## 3. 設計判断の経緯

### 3.1 「案件」の表記採用理由

仕様書 Part 1〜4 では `Product`（品番カルテ）がシステム中核として定義されている。データモデル上「案件」という独立エンティティは存在せず、「Product 1 件 = 案件 1 件」という対応関係になる。

サイドバー上の表記としては、

- 「品番カルテ」: 内部用語であり、データモデル名そのもの
- 「案件」: スタッフが日常業務で使う自然な表現

の比較の結果、**「案件」を採用**。データモデル上は `Product` を指すという内部認識を維持しつつ、UI 表記は業務用語に合わせる方針とする。

### 3.2 サンプル / 量産を別メニューとする理由

データモデル上、サンプルと量産は同じ `Product` がライフサイクルで遷移する関係である（`Product.status` の値が変化）。

選択肢：
- (a) サイドバー直下に「サンプル」「量産」を別メニューとして並べる
- (b) サイドバーは「案件」1 つで、ページ内タブで切替

実務上、サンプル進行中と量産進行中はスタッフが頻繁に行き来する画面であり、**1 クリックでアクセスできる方が運用効率が高い**ため (a) を採用。

データ的な実装としては、

- `/projects/samples` → `Product.status IN ('SAMPLE_IN_PROGRESS', 'SAMPLE_APPROVED' など)`
- `/projects/production` → `Product.status IN ('ORDER_CONFIRMED', 'IN_PRODUCTION' など)`

のように、同一テーブルへの異なるフィルタを当てる構成となる。

### 3.3 リピート品番の扱い

仕様書では「リピート」は **同じ ModelCode から新規 Product を派生**させる設計（`InquiryType.RECURRING`、`ModelCode.totalRepetitions` で累積）。

サイドバー上は **リピートも「新規 Product」として案件メニューに表示**する。リピートかどうかは画面内のバッジ等で区別する想定。

### 3.4 「サンプルなし → 直接量産」のフロー

仕様書では `InquiryType.DIRECT_SAMPLE` および直接量産パターンが想定されている。この場合は Product の `status` が `SAMPLE_*` フェーズを飛ばして `ORDER_RECEIVING` 等から始まる。

サイドバー的には「量産」メニューに直接表示される動きとなる。

### 3.5 進捗ステータス表示の方針

「生地発注済み」「パターン発注済み」等のフラグは、**PO/WO の存在から自動算出**する方針とする。

理由：
- 発注書が存在すれば「発注済み」とみなすのが業務的に自然
- 別途フラグ列を持たせると、発注書とフラグの整合性管理コストが発生する
- データの真実が 1 箇所（PO/WO テーブル）に集約される

実装イメージ：
- 案件一覧画面で各 Product に対し、`hasPO(productId, category='fabric')` 等の集計クエリを叩く
- パフォーマンスが課題になれば、Product テーブルにキャッシュ列を追加する余地を残す

### 3.6 伝票系を独立グループとした理由

伝票系（見積・発注・納品・請求）は、

- 案件起点でのアクセス（特定 Product の関連伝票を見る）
- 伝票単独での一覧（今月の請求書一覧、未払い発注一覧など）

の両方の用途がある。後者の用途を活かすため、案件配下にぶら下げず**独立グループ**として配置。検索性は「品番・ブランドでフィルタ可能」とすることで、案件起点からの導線も確保する。

### 3.7 マスターを 3 グループに分けた理由

階層構造を直感的に表現するため：

- **クライアント側**: クライアント → ブランド・バイヤー・納品先（クライアント配下にすべて紐づく）
- **仕入先側**: 仕入先と工場が並列、外注と諸経費は工場関連で位置づけ
- **その他**: 上記カテゴリに属さない横断的マスター（モデルコード、商品カテゴリ、素材）

注意点として、データモデル上「外注」「諸経費」は工場の子ではなく独立エンティティ（`ContractorMaster`、`ExpenseCategory`）である。サイドバーでのグルーピングは **UI 上の表現**であり、データの親子関係を示すものではない。

## 4. 仕様書 Part 1〜4 との整合性確認

### 4.1 整合している点

| 項目 | 仕様書側 | 本議事録 |
|---|---|---|
| 5 階層 ID 体系 | INQ → ModelCode → Product → SKU → 取引 ID | 案件 = Product として表現 |
| サンプル製作セット | 1st/2nd/3rd ラウンド管理 | 案件 > サンプル メニュー配下で表現 |
| 発注 3 タイプ | 仕様書 / オンライン / 工場 | 発注（PO/WO）メニューに集約 |
| 伝票検索 | 品番・ブランド・期間等 | 「品番・ブランドで検索可能」と明示 |
| マルチテナント | 全テーブル `companyId` 必須 | サイドバー構成に直接影響なし |

### 4.2 仕様書に追記すべき項目

仕様書 Part 1〜4 には現状、明示的なサイドバー設計の記載がない。Phase 1B 着手時に以下を仕様書に追記または別ドキュメント化する：

- ナビゲーション構造図
- 各メニューと対応するデータエンティティのマッピング
- 権限による表示制御（仕様書 5.7 ユーザー・権限管理 との連携）

## 5. 将来の変更可能性メモ

Phase 1B 以降の実装過程で **再検討する余地がある項目**：

### 5.1 「ダッシュボード」の具体的中身
現時点ではプレースホルダー。実装時に何を表示するか（今月の売上、進行中案件数、アラート等）を別途設計する必要がある。

### 5.2 サンプル / 量産のサブメニュー粒度
「サンプル」「量産」の 2 メニューで足りるか、それとも「サンプル 1st」「サンプル 2nd 以降」「リピート」等にさらに分けるかは、実運用で判断する。

### 5.3 「諸経費」の位置
現状は工場グループ配下の表示としているが、実際の `ExpenseCategory` の使われ方によっては「その他マスター」に移動する可能性がある。

### 5.4 進捗ステータスの集計方法
PO/WO の存在から自動算出する方針だが、パフォーマンス問題が出た場合は Product テーブルにキャッシュ列を追加する案を検討する。

### 5.5 案件一覧の表示項目カスタマイズ
慎太郎さんから「必要に応じて一覧に表示する内容を変更したい」とのご要望あり。Phase 1B 着手時に、ユーザー設定で表示列を選択できる機能の要否を検討する。

### 5.6 モバイル / タブレット対応
PWA 対応の方針（仕様書 Part 4）に従い、サイドバーがモバイル時にどう変形するか（ハンバーガーメニュー、ボトムタブ等）を別途設計する必要がある。
