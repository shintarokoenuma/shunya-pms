### D-38 の理由（3点・Claude の整理）

1. 経理の実作業は「明細を見ながら今日入った分を上から順に入れる」＝クライアント横断。クライアントを特定してから入る今の作りでは、10社分で10往復になる
2. ただし取引先を見るときの「繰越がいくら残っていて直近いつ入金があったか」は文脈として効くので、クライアント詳細の節は消さない
3. 「経理」グループを今作ると、取引から請求だけが抜けて、中身が請求＋入金の2つしかない半端なグループになる。支払（仕入・M-029）と締め（B-123）が入ってからまとめる

★`/payments` は新しいモデルも migration も要らない。既存の `listClientPayments` を clientId 省略可にし、入金ダイアログにクライアント選択を1つ足すだけ。列は 入金番号 / 入金日 / クライアント / 方法 / 摘要 / 金額、フィルタはクライアントと期間、下に合計。

### D-40 の理由（★丸め方を揃えるだけでは解決しないこと）

請求書は**1か月分をまとめて税率ごとに1回だけ**丸める（D-22）。納品書は**1枚ごと**に丸める。したがって丸め方を同じにしても、納品書が複数枚あると合計は一致しない。

例: 2,805 円の納品書が2枚（切り捨ての取引先）

| | 計算 | 税額 |
|---|---|---|
| 納品書 | 280 ＋ 280 | 560 |
| 請求書 | 5,610 × 10% = 561 | 561 |

★この1円のズレは丸めの仕様が正しいゆえに起きる構造的なもの。納品書から税を落とせばズレ自体が消える。適格請求書の要件は請求書側で満たしているため、納品書に税額が無くて困ることはない。

★**実装の前に2点を実測する**（推測で決めない）:
- `DeliveryNote.taxAmount` / `totalAmount` が nullable か。nullable なら計算ごとやめる。NOT NULL なら計算は残して表示だけ落とす
- 納品書フォームの「消費税率」の入力欄を外すか（誰も見ない値を入れ続けるのは不自然なので外す方向）

★納品書 PDF（PR-4）にも同じ判断が効く。

## 2. 参考画面に無い実装上の判断（PR-2c で決めたこと）

v0.9 §2 は参考画面の構造と文言を写したものだが、実装時に画面へ足した・落としたものが5つある。いずれも参考画面には描かれていない。

| # | 判断 | 理由 |
|---|---|---|
| 1 | **候補の表の末尾に「税区分」の select（10% / 非課税）を足した** | 納品書明細に税区分の列が無いため、非課税の行を作る手段が他に無い（D-32） |
| 2 | 単価が未入力の納品書明細は**金額 0・「単価なし」の tag** で候補に出す | 候補から落とすと請求漏れに気づけない。外すのは人が決める |
| 3 | 明細の**色名は `InvoiceItem.description` に写す**（`colorCode` は `colorCode`） | InvoiceItem に色名の列が無い。納品日・納品書番号は読み取り時に納品書明細から引く |
| 4 | **ドラフトの編集画面は作らない** | v0.9 の4画面に無い。ドラフトは取消して作り直す |
| 5 | 入金の**摘要は `Payment.description`** に保存（`title` は使わない） | 1つの自由記述に2つの器を使い分ける理由が無い |

★**`PDF` ボタンは参考画面に描いてあるが作っていない**（PR-4 のスコープ・v0.9 §2-3 のとおり）。
