# B-124 明細 id の不安定性（伝票編集による全削除→再作成）記録ノート v0.1（2026-08-08）

- 種別: 記録ノート（構造的課題の記録。是正の可否は未判断）
- 起点: B-108 PR2 recon（2026-08-08）で**3例目**に遭遇したため、
  個別の回避策ではなく構造的課題として記録することにした
- 状態: **是正するとは決めていない。** 影響範囲が広く、単独で着手する話ではない

---

## 1. 事象

`PurchaseOrder` / `WorkOrder` / `DeliveryNote` の更新 action は、
明細を**全削除してから再作成**する。明細の `id` は `@default(uuid())` のため、
親を一度編集しただけで**明細の id がすべて別物に入れ替わる。**

| action | 該当箇所 | 対象 |
|---|---|---|
| `updatePurchaseOrder` | `src/lib/actions/purchase-orders.ts:732-733` | `PoItem` |
| `updateWorkOrder` | `src/lib/actions/work-orders.ts:940-941` | `WoItem` |
| `updateDeliveryNote` | `src/lib/actions/delivery-notes.ts:709-710` | `DeliveryNoteItem` |

いずれもトランザクション内で `deleteMany` → `createMany`。
明細モデルは `deletedAt` を持たず親従属（`onDelete: Cascade`）。

## 2. これまでの遭遇履歴（3例）

1. **QE-1（原価参照）**: コスト集計の参照先を `poItemId` ではなく
   `purchaseOrderId` にする、と確定した。理由がこの不安定性。
2. **B-108 PR2（引き当て元の記録）**: 納品書明細に引き当て元を記録するにあたり、
   行 id が dead になるため親伝票 id を併記する（案A′・5列）ことで回避。
3. **`updateDeliveryNote` 自身**: 納品書を編集すると、上記2で追加した
   引き当て元の記録そのものが消えうる。フォームでの持ち回り（round-trip）で回避。

**同じ回避策を3箇所で書いている。** 4例目が出る前提で記録を残す。

## 3. 何が起きるか

- 明細 id を外部から参照している箇所は、親が編集された瞬間に参照先を失う。
- **失ったことがエラーにならない。** FK を張っていない scalar 参照のため、
  黙って「見つからない」状態になる。
- したがって参照側は毎回「見つからない場合の安全側の挙動」を自前で決める必要がある
  （B-108 PR2 では「判定不能は未納品側に倒す」と明文化）。

## 4. 是正するとしたらの選択肢（未評価・メモのみ）

- **案1: id 維持の upsert に変える。** 既存行は id を保ったまま update、
  削除された行のみ delete、新規行のみ create。
  → 影響範囲が広い（3 action ＋ 各フォームの行 id 持ち回り）。
     行の並べ替え（B-084）との相互作用も要検討。
- **案2: 明細に業務キーを持たせる。** `itemOrder` は編集で変わるため不可。
  安定した業務キーが何になるかは不明。
- **案3: 現状維持＋親 id 併記を house style として明文化する。**
  最も安価。ただし参照側が毎回回避策を書き続けることになる。

## 5. 判断の材料になる問い（次に検討する時に）

- 明細 id を参照したい箇所は今後も増えるか（B-109 請求・B-114 量産納品で増える見込み）
- 締め処理（B-123）で赤伝方式を採ると、訂正伝票が元伝票の**行**を参照する必要が出るか
- FK を張らない house style を続ける限り、参照の破綻は静かに起きる。これを許容できるか

## 6. 現時点の方針

**B-108 PR2 では案3（親 id 併記）で進む。** 是正の判断は B-109 着手時に、
請求側で明細 id 参照が必要になるかを見てから行う。
